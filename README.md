# OutlookMailBackup

Windows **클래식 Outlook**의 메일을 Unicode MSG 파일로 보관하고, 기존 MSG와 신규 백업을 계정 폴더의 `yyyy\mm` 아래로 정리하는 단일 VBA 모듈입니다.

**현재 버전: 3.5.1** · 실행 매크로: **`MB_01_RunBackup`** 하나

[OutlookMailBackup.bas 다운로드](OutlookMailBackup.bas?raw=true) · [검증 결과와 한계](docs/VALIDATION.md) · [2026-11-12 최종 검토](docs/FINAL_REVIEW_20261112.md)

> 이 버전의 재현 가능한 검사와 대상 BAS 해시는 [검증 결과](docs/VALIDATION.md)에 기록합니다. Python 모델·소스 계약 검사, 구조 검사와 실제 Outlook 실행을 구분합니다. 실제 Windows Outlook의 VBA 컴파일, 실제 MSG 호환성 및 10만 건 성능 시험은 아직 실행하지 않았습니다. 설치 후 대상 PC에서 `Debug > Compile VBAProject`를 확인해야 합니다.

## 설치와 실행

1. 위의 **`OutlookMailBackup.bas` 한 파일**을 내려받습니다. `development/`의 조각 파일은 가져오지 않습니다.
2. 클래식 Outlook에서 `Alt+F11`을 눌러 VBA 편집기를 엽니다. 이미 같은 이름의 `OutlookMailBackup` 모듈이 있다면 이전 모듈을 내보내 보관한 뒤 제거합니다.
3. `File > Import File`로 새 BAS를 가져오고, `Debug > Compile VBAProject`를 실행합니다. 컴파일 오류가 있으면 해당 오류를 먼저 해결합니다.
4. VBA 프로젝트를 저장합니다. 매크로 실행은 조직의 보안 정책에 따라 허용합니다.
5. Outlook의 매크로 목록에서 **`MB_01_RunBackup`**을 실행합니다. 이후에도 이 매크로만 실행하면 됩니다.
6. 사용할 수 있는 저장 경로가 기억되어 있지 않으면 폴더 선택 창이 나타납니다. 기존 백업을 이어 쓰려면 사용할 **기준 폴더**와 기존 MSG가 들어 있는 **계정 폴더**를 선택합니다. 처음 사용하는 기준 폴더에는 `MailBackup` 관리 폴더가 생깁니다. 소유권과 계정 연결이 확인된 경로는 다음 실행부터 재사용합니다.

각 VBA 세션의 첫 실행은 임시 파일과 합성 미발송 메일을 사용한 환경 검사를 먼저 수행합니다. 이 검사에 실패하면 실제 보관 작업을 시작하지 않습니다. 설정, 복구, 연·월 정리, 기존 파일 연결, 증분 백업의 별도 실행 순서는 없습니다.

**중지:** 실행 중 같은 매크로를 다시 실행하거나 `<관리 루트>\STOP.txt`를 만들면 취소를 요청합니다. 현재 안전 단위의 처리가 끝나고 정리가 완료될 때까지 기다립니다. `STOP.txt`로 중지했다면 다음 실행 전에 해당 파일을 제거합니다. 실행 중 VBA의 `End` 또는 `Reset`으로 강제 종료하지 않습니다.

## 처리 범위

기본 자동 작업은 Outlook의 **기본 저장소(DefaultStore)**와 그 하위 폴더에 있는 일반 `MailItem`을 대상으로 합니다. 다른 PST, 공유 사서함, 별도 온라인 저장소가 자동으로 모두 포함되는 것은 아닙니다. 하나의 관리 루트는 하나의 `StoreID`에 연결됩니다.

새 Outlook, Mac Outlook 및 서버에서 Outlook을 자동화하는 용도는 지원하지 않습니다. 첨부파일은 MSG 내부에 보관하며, 별도 파일로 추출하는 기능은 기본적으로 꺼져 있습니다.

## 폴더 구성과 경로 재사용

| 위치 | 용도 |
| --- | --- |
| `<기준 폴더>\MailBackup\State\` | 활성 인덱스, 해시 증거, 작업 기록, 검사 상태 |
| `<계정 폴더>\yyyy\mm\*.msg` | 기존 및 신규 메일의 실제 MSG 파일 |
| `<계정 폴더>\_Recovery\` | 독립된 메타데이터 스냅샷, 복구 계획, 보존된 기록 |
| `%LOCALAPPDATA%\OutlookMailBackup\locations\base_<StoreID SHA256>.tsv` | 저장소별 기준·관리·계정 폴더 위치 기억 |
| `<기준 폴더>\MailBackup\State\runs\<실행 ID>\summary.txt` | 실행별 결과와 처리 시간 |
| 같은 실행 폴더의 `review.tsv` | 관측된 경고·오류의 원인 코드, 제목·경로, 권고 조치 |

신규 기본 이름에는 버전 숫자를 붙이지 않습니다. 이미 운영 중인 `SafeV2`는 기존 `_MailBackup_Data`·`_MailBackup_Recovery` 조합을 그대로 읽습니다. 이전 `_state` 기록은 검증된 복사로 이관하며, 살아 있는 새 상태를 오래된 기록으로 덮어쓰지 않습니다. 새 이름과 옛 이름의 서로 다른 기록이 함께 있으면 임의로 합치지 않고 검토합니다.

폴더 조합은 소유권 표식에 `Modern` 또는 `Legacy`로 명시하고 체크섬이 있는 사용자 설정에도 기억합니다. **예전 사용자 지정 관리 루트의 이름이 `MailBackup`이어도 기존 구조를 유지합니다.** 이름만으로 운영 폴더를 바꾸지 않습니다. 남은 표식과 설정이 충돌하거나 이전 일반 Schema4 `MailBackup` 루트의 구조를 입증할 단서가 모두 사라졌다면, 추측해서 쓰지 않고 검토를 요구합니다.

경로는 사용자 설정, 저장소별 위치 파일, 계정·복구 표식 등으로 확인합니다. 경로가 사라졌거나 연결을 입증할 수 없을 때만 다시 선택합니다. 모든 설정과 정확한 위치 단서가 삭제되면 기존 폴더를 한 번 다시 지정해야 합니다. 다른 계정의 표식과 충돌하면 자동으로 선택을 확정하지 않습니다.

`_Recovery`는 **MSG 사본을 보관하는 폴더가 아닙니다.** 메타데이터를 복구할 수 있어도 삭제된 MSG나 고장 난 디스크의 내용을 되살릴 수는 없습니다. 실제 아카이브 전체의 별도 백업은 이 기능과 구분됩니다.

## 상대 경로와 기준 경로

코드에 개인 PC의 드라이브·출력 경로를 고정하지 않습니다. 선택한 기준·계정 폴더를 기억하고, 새 `MBS4` 저널에는 `2026\11\제목.msg`처럼 **계정 폴더 아래의 상대 파일 경로**를 씁니다. 신규 저장, 기존 MSG 등록, 재가져오기 별칭에 같은 원칙을 적용합니다. 기존 MBS2/MBS3 기록은 원문과 체크섬을 보존해 읽습니다.

상대 경로는 디스크 작업 직전에 정확한 계정 루트와 결합합니다. `..`, 절대 경로, UNC, ADS와 안전하지 않은 경로 구성 요소를 상대 경로 필드에 넣을 수 없습니다. `SaveAs`는 이 검증으로 얻은 전체 임시 경로를 받으므로 현재 작업 폴더에 따라 저장 위치가 달라지지 않습니다.

계정·관리 루트의 소유권 연결과 기존 이동·복구 증거에는 절대 경로가 남습니다. 이는 다른 계정이나 디스크를 잘못 연결하지 않기 위한 기준입니다. **폴더를 임의 이동해도 곧바로 이어 쓰는 포터블 아카이브 기능은 아닙니다.** 상세 저장 계약은 [폴더와 경로 설계](docs/PATHS.md)에 정리했습니다.

## 기존 파일·신규 파일·복구 시나리오

| 상황 | 동작 |
| --- | --- |
| 기존 MSG가 계정 폴더에 평면으로 있거나 일부 하위 폴더에 정리됨 | 재귀적으로 확인하고, 검증된 이동 계획에 따라 `yyyy\mm`로 정리 |
| 같은 메일의 기존 MSG가 확인됨 | 기존 파일을 연결·재사용하며 `MailItem.SaveAs`를 반복하지 않음 |
| 신규 메일 | 같은 디렉터리의 임시 파일에 저장한 뒤 재열기·내용·크기·해시를 확인하고 최종 파일로 게시 |
| 기존 메일을 Outlook에 다시 넣어 EntryID가 바뀜 | 같은 StoreID의 기존 증거와 지원하는 내용 비교가 일치하면 기존 MSG에 연결 |
| 같은 원본 메일의 내용이 실제로 변경됨 | 이전 버전과 변경을 입증할 수 있으면 별도 리비전으로 보관 |
| 설정만 삭제됨 | 남은 위치 파일과 정확한 소유권·계정 표식으로 복원하거나 경로를 다시 선택 |
| 활성 운영 파일 일부 또는 전체가 삭제됨 | 검증된 복구 세대와 살아 있는 기록을 조합하고, 재조정을 완료할 때까지 복구 필요 상태 유지 |
| 파일 크기는 유지됐지만 과거 저널·이동·기준선 행이 삭제·대체됨 | 스냅샷 당시 구간의 원시 바이트 해시로 탐지하고 과거 증거와 잔존 기록을 보존하여 복구 |
| MSG만 남고 이전 인덱스·해시가 모두 사라짐 | 읽을 수 있는 MSG의 현재 바이트를 `MSG_ONLY_REBASELINED`로 등록; 과거 무결성을 복원했다고 표시하지 않음 |
| 인덱스에 있는 MSG가 누락·변조되거나 증거끼리 충돌함 | 자동 재내보내기·덮어쓰기를 진행하지 않고 검토 대상으로 남김 |
| 작업 취소 또는 중단 후 다시 실행 | 검증된 계획과 기록으로 재개; 증명되지 않은 임시 파일과 충돌 기록은 보존하고 검토 대상으로 처리 |

이는 **이전 출력물을 새 버전에서 검증해 이어 쓰는 호환성**입니다. MBS2/MBS3를 읽는 순방향 호환을 유지하며, MBS4를 기록하기 전에 소유권 표식을 `Schema4.Modern` 또는 `Schema4.Legacy`로 전환합니다. 이전 일반 `Schema4` 표식도 읽습니다. 모든 과거 스크립트와의 상호 쓰기 호환성을 보장하지 않습니다. 새 상태 형식으로 전환한 후에는 이전 매크로와 새 매크로를 번갈아 실행하지 않습니다.

파일명이나 Internet Message-ID만으로 같은 메일이라고 판단하지 않습니다. 지원하는 본문·수신자·헤더·첨부파일 등을 함께 비교합니다. 다른 StoreID, 불명확한 옛 파일, 지원하지 않는 특수 첨부파일 등은 `REVIEW`가 될 수 있습니다. 이 경우 “다시 내보내지 않았다”와 “백업이 완전하게 확인되었다”는 서로 다른 결과입니다.

## 연·월 기준과 Everything 검색

신규 파일명은 `yyyyMMdd_HHmmss_보낸사람_제목.msg` 형식을 사용합니다. 기존 파일명은 필요한 충돌 접미사를 제외하고 유지합니다. 같은 이름의 파일이 만나도 기존 파일을 덮어쓰지 않습니다.

연·월은 유효한 `SentOn`을 우선하고, 없으면 `ReceivedTime`, `CreationTime` 순으로 결정합니다. 인식 가능한 기존 `YYYYMMDD_HHNNSS` 파일명은 기존 분류 날짜를 유지합니다. 파일시스템의 수정 시각으로 보관 월을 정하지 않습니다.

새 파일의 제목은 보수적인 **전체 경로 235 UTF-16 단위** 예산 안에서 가능한 만큼 포함합니다. 고정된 40자 제목 제한은 없지만, Windows 금지 문자 정리와 긴 제목의 잘림은 발생할 수 있습니다. 계정 폴더 경로는 80 UTF-16 단위 이내여야 합니다. 잘린 제목의 나머지는 MSG 내부의 전체 제목에 남으며, 파일명에 없는 부분은 Everything의 파일명 검색으로 검색할 수 없습니다.

## 자동 백업 범위와 처리 시간

최근 1개월로 범위를 고정하지 않습니다. 매 실행마다 기본 저장소의 가벼운 메타데이터 목록을 확인하고 다음 규칙으로 실제 비교·저장 대상을 고릅니다.

- 정상 실행 기록이 있으면 **마지막 성공한 스캔의 시작 시각(UTC)에서 7일 전**부터 겹쳐 확인합니다. 오래 실행하지 않았다는 이유로 30일 또는 90일에서 잘라내지 않습니다.
- 최초 실행은 최근 30일을 기본 범위로 사용하면서, **알 수 없는 메일 식별자와 변경된 수정 표식**은 과거 날짜여도 대상으로 포함합니다. 오래된 메일을 새로 가져온 경우도 이 경로로 포착합니다.
- 시계 역행, 시간대 규칙·비교 정책 변경, 상태 복구 등은 전체 현재 메일 재조정을 요구합니다.
- 과거 원본 비교와 실제 보관 파일 검사는 별도 순환 예산으로 계속 진행합니다. 기본 순환은 각각 실행당 최대 500건이며, 발견된 문제는 후속 재검토 상태를 유지합니다.

정상 완료 이력이 있는 아카이브에서 **전체 목록과 선택한 작업을 끝냈지만 개별 REVIEW만 남은 경우**, 그 실행의 시작 시각을 보조 선별 캐시에 기억할 수 있습니다. 다음 실행은 해당 시각에서 7일을 겹쳐 비교하되, REVIEW의 개별 재시도·알 수 없는 메일·변경된 메일·이전 비교 정책·순환 검사는 계속 선택합니다. 기존 성공 시각과 저널·검사 기록의 SHA-256, 루트·StoreID·시간대·정책이 모두 맞을 때만 적용합니다. 최초 실행·복구·전체 재검사에서는 사용하지 않고, 캐시 발행 시점까지 확인된 취소·오류·미처리가 있으면 새 캐시를 발행하지 않습니다. 이전 캐시는 증거가 계속 일치할 때만 재사용할 수 있습니다. 캐시가 없어지거나 검증되지 않으면 기존 성공 범위로 돌아갑니다. **이 캐시는 성공 완료 시각을 앞당기지 않으며 REVIEW를 해결한 것으로 처리하지 않습니다.**

캐시를 기록한 뒤 마지막 스냅샷 작성이나 잠금 해제에서 오류가 나면, 캐시가 남아 있어도 최종 실행은 `FAILED`가 될 수 있습니다. 캐시 존재 여부로 성공을 판단하지 않고 최종 팝업과 `summary.txt`를 확인합니다. 남은 캐시도 다음 실행에서 모든 증거를 다시 확인한 뒤에만 사용합니다.

전체 메타데이터 순회와 실제 `SaveAs` 대상 선별은 별개입니다. 기존 파일 재사용은 저장 비용을 줄이지만 해시, 본문 비교, 복구, 연·월 이동, 검사 및 스냅샷 비용이 없어지는 것은 아닙니다. 특히 처음으로 MSG만 남은 아카이브를 복구하면 각 파일을 해시하고 열어야 하므로 이후 증분 실행보다 오래 걸릴 수 있습니다.

v3.5.1의 과거 증거 연속성 검사는 이전 저널·이동·기준선 구간을 순차적으로 읽어 해시합니다. 파일 크기에 비례한 추가 I/O가 있으며, 버퍼는 최대 64 KiB입니다. 반복 REVIEW 선별 최적화로 줄이는 메일 비교 비용과 이 검사 비용은 구분해야 합니다.

같은 제목의 메일은 Message-ID·발송 시각을 이용한 보조 색인으로 반복 탐색을 줄입니다. 최종 동일성 판정은 계속 본문·첨부파일·과거 해시를 확인합니다.

실행 보고서는 신규 저장(`NEW`)과 기존 파일 재사용(`REUSE`)의 시간을 구분합니다. 일반 성공 표본이 30개 이상일 때 10만 건의 **항목 처리 비용**을 예측하며, 목록 수집·복구·이동·검사 시간은 추가 비용입니다. 실제 10만 건 부하 시험 결과는 아직 없습니다. 관측값이 없으면 `NOT_MEASURED`입니다.

## 결과 확인

완료 팝업과 `summary.txt`에서 신규, 재사용, 실패, 검토 필요, 미처리 건수 및 현재 메일 범위의 완료 상태를 확인합니다. `PARTIAL`은 검토 또는 미완료 항목이 남아 있다는 뜻이며, 어떤 원인인지 상세 보고서를 함께 읽어야 합니다. 현재 메일 범위, 물리적 파일 무결성, 현재 바이트만으로 복원한 기준선은 서로 다른 상태로 보고합니다.

같은 실행 폴더의 `review.tsv`는 원인 코드와 가능한 제목·경로·후속 조치를 제공합니다. **행 수는 고유 미해결 메일 수가 아닙니다.** 뒤에서 해결된 경고나 같은 메일의 여러 경고도 포함될 수 있습니다. `HISTORY_CUTOFF`, 파일 누락·해시 변경, 증거 충돌, 제한된 내용 검증 등을 구분한 절차는 [REVIEW 안내](docs/REVIEW_GUIDE.md)를 참고합니다. 이 보고서를 수정하거나 지워도 백업 증거나 재시도 의무는 바뀌지 않습니다.

기본 비교는 모든 MAPI 속성의 완전한 동일성을 보증하지 않습니다. 사용자 정의 `UserProperties`가 있으면 신규 파일은 제한된 검증 상태가 될 수 있고, 기존 파일과의 동일 내용 연결은 보류됩니다. 플래그, 작업, 알림, 읽음 상태, 임의 MAPI 속성 및 모든 특수 첨부파일은 인증 범위가 아닙니다. 자세한 경계는 [검증 문서](docs/VALIDATION.md)를 참고합니다.

## 개발 및 재현

사용자는 BAS만 필요합니다. 개발용 조각·모델 검사는 `development/`, 조립·검증 도구는 `tools/`에 있습니다. Python 3.10 이상에서 다음 명령으로 배포 파일과 검사를 확인할 수 있습니다. 이 배포본은 Python 3.12 환경에서 재현을 확인했습니다.

```sh
python -B tools/verify.py
```

`verify.py`는 배포 BAS 재생성, 세 가지 VBA 조건 분기의 구조 검사, 현재 검증 보고서의 해시 일치, 검증기 자체의 결함 주입 검사, 메일 모델·소스 계약 검사를 실행합니다. 건너뛴 검사와 오래된 증거를 통과로 계산하지 않습니다. [검증 도구 설명](docs/VALIDATION_TOOLING.md)과 [GitHub Actions](https://github.com/greatgc-flow/OutlookMailBackup/actions)을 참고할 수 있습니다. Windows runner의 Python 검사는 Outlook 실행을 대신하지 않습니다.

배포 BAS는 ASCII 소스와 CRLF 줄바꿈을 사용합니다. 현재 파일의 크기·SHA-256과 실제 검사 결과는 [검증 기록 JSON](docs/validation.json)에 묶어 보존합니다.

주요 동작·제한은 [배포 BAS의 머리말](OutlookMailBackup.bas)에도 포함되어 있습니다. Outlook의 저장 API는 Microsoft의 [MailItem.SaveAs 문서](https://learn.microsoft.com/en-us/office/vba/api/outlook.mailitem.saveas)를 참고할 수 있습니다.
