# 시나리오와 검증 범위

각 시나리오는 **입력 판별 → 증거 확인 → 작업 → 기록 → 재실행**을 연결해 검토합니다. 동일 내용 여부를 입증하지 못한 결과는 성공이나 자동 재내보내기로 바꾸지 않습니다. 다음 표의 근거는 코드·Python 모델·소스 계약이며, 실제 사용자 Outlook 아카이브에서 실행한 결과는 별도로 필요합니다.

## 메일 상태별 처리

| 입력 상태 | 기대 동작 | 반복 실행·중단 시 유지할 조건 | 주요 검사 |
| --- | --- | --- | --- |
| 기존 MSG만 존재 | 현재 바이트를 확인해 기준선과 연결 후보를 생성 | 과거 해시가 복원됐다고 표시하지 않음 | recovery proof / recovery merge |
| 기존 MSG와 유효한 인덱스 | 해시·내용 정책에 따라 재사용 | 같은 파일을 다시 SaveAs하지 않음 | policy upgrade / revision |
| 신규 메일 | 임시 저장 → 다시 열기 → 검증 → 최종 게시 → 인덱스 | 미완료 단계를 성공으로 세지 않음 | recovery proof / source contracts |
| 기존 메일을 다시 가져와 EntryID 변경 | 같은 StoreID의 검증된 기존 파일과 비교 | 파일명·Message-ID만으로 동일 판정하지 않음 | index alias |
| 같은 원본 메일의 내용 변경 | 과거 바이트가 여전히 유효하면 별도 리비전 후보 처리 | 과거 기대 해시를 현재 바이트로 교체하지 않음 | revision / index alias |
| 현재 내용이 이전 버전으로 되돌아감 | 기존의 동일 내용 파일을 다시 연결할 수 있음 | 비교·최종 파일 가드를 생략하지 않음 | revision / index alias |
| 같은 제목이 대량 존재 | 날짜·ID·발송 시각 보조 색인으로 후보 선택 | 새 후보만 색인에 추가; 모호한 경우 REVIEW | index alias |
| 헤더가 없거나 ID 존재 여부가 바뀜 | 가능한 후보를 보수적으로 유지 | ID가 다르게 보인다는 이유로 후보를 누락하지 않음 | index alias |
| 기존 파일 누락·해시 불일치 | 검토·복구 대상으로 유지 | 새 파일로 몰래 덮거나 과거 증거를 재기준화하지 않음 | recovery proof / revision |
| 동일 인덱스 키의 충돌한 증거 | 일반 로딩·복구·쓰기 모두 거부 | 저널 기록 전 거부하고 기존 캐시·파일 보존 | index alias |
| 지원하지 않는 사용자 속성·특수 첨부 | 제한 검증 또는 REVIEW | 전체 MAPI 동일성으로 표시하지 않음 | fidelity |

## 운영 파일과 경로 상태별 처리

| 환경 상태 | 기대 동작 | 재실행의 기준 | 주요 검사 |
| --- | --- | --- | --- |
| 최초 사용, 운영 폴더 없음 | 선택한 기준 아래 `MailBackup\State` 생성 | 선택한 계정과 관리 루트를 기억 | settings / layout |
| 기존 계정 폴더에 평면·부분 정리된 MSG | 검증된 이동 계획으로 `yyyy\mm` 정리 | 원래 파일명과 충돌 증거 보존 | layout / 기존 이동 계약 |
| 사용자 설정만 삭제 | 남은 위치 파일·정확한 표식으로 경로 재발견 | 이름이 비슷하다는 이유로 다른 계정 선택 금지 | settings |
| 모든 위치 단서 삭제 | 사용자에게 실제 기존 폴더 선택 요청 | 선택 후 소유권·StoreID 재검증 | settings |
| 활성 상태 일부·전체 삭제 | 스냅샷과 살아 있는 기록으로 복구 | 완전 재조정 의무가 종료될 때까지 유지 | recovery merge |
| 복구 폴더 삭제 | 활성 기록을 보존하고 검증 가능한 세대를 다시 구성 | 기존 파일 바이트를 새 해시로 정당화하지 않음 | recovery proof / layout |
| 활성·복구 메타데이터가 모두 없음 | 읽을 수 있는 MSG를 현재 바이트 기준으로 등록 | `MSG_ONLY_REBASELINED`와 과거 검증을 구분 | recovery proof |
| 새 이름·옛 이름의 기록이 동시에 존재 | 모호한 두 기록을 자동 병합하지 않음 | 선택한 계정·관리 루트와 정확히 연결된 증거 필요 | layout |
| 관리 폴더가 junction/symlink | 쓰기 시험·잠금·소유권 쓰기 전에 거부 | 중요한 쓰기 경계에서 경로를 다시 확인 | path |
| MBS2/MBS3/MBS4 혼합 저널 | 각 형식을 검증하고 같은 내부 계약으로 해석 | 원문·체크섬과 기존 기대 바이트를 보존 | relative / index alias |
| `..`·UNC·ADS 등을 넣은 상대 경로 | 해석·게시 전에 거부 | 다른 폴더로 경로가 탈출하지 않음 | relative |
| 사용 취소·프로세스 중단 | 완료된 증거와 미완료 계획을 구분 | 같은 계획의 확인된 단계에서 재개 | recovery merge / recovery proof |
| 알 수 없는 체크섬 포함 형식 | 보존 후 검토 | “손상 행”으로 간주해 임의 폐기하지 않음 | recovery merge |

## 시간·범위·성능

최근 1개월로 자르지 않습니다. 마지막 성공한 스캔의 UTC 시작 시각에서 7일을 겹쳐 확인하고, 오래된 날짜라도 알 수 없는 식별자와 변경된 수정 표식을 다시 검토합니다. 시간대 규칙·정책 변경과 상태 복구에는 전체 현재 메일 재조정이 적용됩니다. 메타데이터를 바꾸지 않는 공급자의 내용 변경은 별도의 순환 내용 검사 범위에 해당합니다.

대량의 같은 제목 메일에 대한 새 색인은 이전 전체 순회 판정과 결과를 비교하고, 100,000개 합성 기록에서 방문 횟수를 셉니다. 이것은 Python 알고리즘 모델이며 Outlook·디스크 처리 시간을 측정한 값이 아닙니다. 실제 보고서의 NEW/REUSE 표본 추정도 전체 실행 시간과 구분합니다.

## 실패·성공 판정의 경계

모델에서 상태 전이가 닫혀 있다는 사실은 모든 Outlook 공급자·MSG 변형·하드웨어 장애를 실행해 검증했다는 뜻이 아닙니다. 저장 공간 부족, 권한 변경, 실제 전원 손실, COM 오류와 모든 첨부 유형에 대한 실행 결과는 환경별로 확인해야 합니다. 악의적인 외부 프로세스가 경로 이름 공간을 계속 바꾸는 모든 시점을 원자적으로 막는다고 주장하지 않습니다.

원본 메일을 삭제하는 기능은 없습니다. 메타데이터 복구는 삭제된 MSG 내용을 복원하는 기능이 아닙니다. 실제 환경에서 확인할 절차는 [Outlook 검증](OUTLOOK_VALIDATION.md)에 정리했습니다.
