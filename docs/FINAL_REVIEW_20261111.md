## 중요한 발견 사항

### R01 — 부분 복원 조합에서 스냅샷에만 남은 과거 증거를 재발견하지 못할 수 있음

**P2, 정적 호출 경로상 조건부 공백. 실제 Outlook/파일시스템에서의 실행 재현은 하지 않았습니다.**

`MBR_StateHealthy`는 각 활성 상태 파일의 행 체크섬·구조·존재와 append-only 파일이 스냅샷보다 짧아졌는지를 확인합니다. 활성 저널이 스냅샷의 정확한 이전 바이트 또는 같은 과거 증거 집합을 유지하는지까지 비교하지는 않습니다. healthy이고 pending 복구 계획이 없으면 `MBR_RestoreState`는 스냅샷의 개별 과거 행을 합치지 않고 종료합니다.

이후 `MBR_BuildBaseline`은 활성 인덱스, 활성 baseline, 살아 있는 게시 단계 증거를 사용합니다. dormant snapshot/chunks의 개별 옛 저널 행을 찾는 경로는 없습니다. 다음 조건이 함께 성립하면 현재 파일이 `MSG_ONLY_REBASELINED`로 등록될 가능성이 있습니다.

1. 스냅샷에는 해당 MSG의 과거 기대 해시가 남아 있음.
2. 부분 복원·수동 편집 등으로 활성 저널에서 그 행이 빠졌지만 다른 유효 행 때문에 총 크기는 스냅샷 이상임.
3. 다른 활성 상태 파일도 존재·체크섬·구조·크기 조건을 통과하고 pending 복구 의무가 없음.
4. 그 MSG를 가리키는 다른 활성 인덱스 기록도 없고, 독립 활성 baseline·게시 단계·미해결 검사 증거도 남아 있지 않음.
5. 현재 MSG가 계정 폴더 안에 있고, 바이트가 달라졌어도 여전히 읽을 수 있음.

**저널 한 행 삭제만으로 보통 발생하는 문제는 아닙니다.** 새 출력의 primary/mirror 게시 증거나 기존 MSG의 활성 baseline이 살아 있으면 과거 해시를 유지하는 별도 방어가 작동합니다. 과거 저널만 증거로 가진 형식이나 여러 기록을 서로 다른 시점으로 부분 복원한 조합이 주요 검토 대상입니다.

권고: 새 baseline을 만들기 전에 스냅샷의 과거 증거까지 필요에 따라 조회하거나, append-only 과거 구간의 연속성을 입증하도록 보완합니다. 독립 proof가 남은 경우와 사라진 경우를 나눈 결함 주입 검사 및 실제 파일 복원 시험으로 닫아야 합니다.

근거: [mb_recovery.basfrag](../development/mb_recovery.basfrag)의 `MBR_FindSnapshot`, `MBR_StateHealthy`, `MBR_RestoreState`, `MBR_LoadBaseline`, `MBR_MergeStageProof`, `MBR_BuildBaseline`, `MBR_CaptureBaseline`.

### R02 — 이전 사용자 지정 관리 루트 이름이 MailBackup이면 legacy 상태와 충돌

**P2, 소스로 확인한 호환 예외와 설명 범위의 불일치입니다.**

`MBS_IsModernLayout`은 관리 루트의 마지막 폴더명이 `MailBackup`이면 modern으로 판정합니다. 과거 소유권이 확인된 사용자 지정 루트라도 그 이름을 이미 사용하고 `_MailBackup_Data`에 기록이 있다면 새 코드가 `State`를 기대하여 `MBS_ValidateLayout`에서 1210 오류로 중단합니다.

경로 사전 확인에서 중단하므로 이 발견은 기존 파일을 덮어쓰는 결함이 아닙니다. 그러나 기존 사용자 지정 관리 루트를 모두 그대로 이어 쓸 수 있다는 설명에는 이 예외가 필요합니다. **SafeV2를 한 번도 실행하지 않은 신규 설치의 MailBackup/State/_Recovery 흐름에는 직접 영향이 없습니다.**

권고: 이전 layout의 명확한 증거를 판정에 포함하거나 이 예외의 이관 절차를 설계합니다. 두 layout의 서로 다른 기록이 있는 경우 자동으로 합치는 방식은 피하고, 설정·운영 폴더가 삭제돼도 선택이 흔들리지 않는지 함께 확인해야 합니다.

근거: [mb_operating.basfrag](../development/mb_operating.basfrag)의 `MBS_IsModernLayout`, `MBS_DataLeaf`, `MBS_ValidateLayout`; [mb_paths.basfrag](../development/mb_paths.basfrag)의 `MBP_TryBackupBase`; [기존 설명](PATHS.md)의 이전 사용자 지정 루트 표.

### R03 — 과거 메일을 찾았어도 자동 SaveAs가 보류될 수 있음

**P2, 중복 방지를 위한 의도된 보수 정책이며 자동 완료의 제한입니다.**

AUTO는 unknown source와 변경된 수정 표식을 날짜에 상관없이 선별합니다. 그러나 `MB_NewExportAllowed`는 기존 MSG가 있고 미대응 메일의 유효 날짜가 기존 아카이브 최신 `DateLastModified` 이하이면 SaveAs를 거부합니다. 식별에 사용할 파일명/발송 시각을 읽을 수 없는 기존 MSG가 하나라도 있으면 미대응 메일도 검토 대상으로 남깁니다.

따라서 복사·복원 과정 등으로 파일 수정 시각이 최근으로 바뀌었거나, 백업된 적 없는 과거 메일을 새로 가져온 경우 탐지됐더라도 `REVIEW`가 될 수 있습니다. 이때 원본을 삭제하거나 파일을 덮지는 않지만 현재 메일 전체가 백업 완료된 것은 아닙니다.

권고: REVIEW별 근거와 안전한 해소 절차를 사용자에게 제공하고, 필요한 경우 확인된 신규 내보내기만 허용하는 절차를 설계합니다. 파일 수정 시각 차단을 단순 제거하거나 미확인 결과를 COMPLETE로 바꿔 점수를 높이면 안 됩니다.

근거: [mb_window.basfrag](../development/mb_window.basfrag)의 `MBW_ShouldQueue`; [mb_reuse.basfrag](../development/mb_reuse.basfrag)의 `MB_NewExportAllowed`; [mb_legacy.basfrag](../development/mb_legacy.basfrag)의 `MBL_BuildIndex`.

### R04 — REVIEW 지속 시 반복 비용과 순환 검사의 검출 지연

**P2, 안전성과 처리 비용 사이의 운영상 제한입니다.**

`MBW_CanCommit`는 현재 처리의 `gMailReview`, `gContentReview` 등이 남으면 성공 범위를 전진시키지 않습니다. 오래 남는 제한 검증/REVIEW 항목 때문에 같은 기간을 반복 확인할 수 있습니다. 이는 개별 재시도 의무를 유지하는 것과 별개로 전체 성공 범위의 비용에 영향을 줍니다.

과거 원본 비교와 물리 보관 파일 검사는 각각 실행당 최대 500건을 순환합니다. 고정된 100,000개 대상을 이 순환 경로만으로 한 번씩 방문한다고 가정하면 `ceil(100000/500)=200회` 실행 분량입니다. 이는 새 메일·변경 메일의 총 처리 한도가 500건이라는 뜻도, 실제 완료가 반드시 200회라는 뜻도 아닙니다. 추가 선별·재시도·취소·대상 변화가 따로 영향을 줍니다.

불명확한 동일 제목 후보는 최대 128개까지 상세 확인하며, 한도 초과 시 REVIEW로 둡니다. 증분 실행도 전체 메타데이터와 파일/상태 확인 비용이 있고 최초 MSG-only 복구에는 전체 해시·재열기 비용이 있습니다.

권고: 개별 재시도 의무의 무손실 보존을 전제로 범위 진행 비용을 측정하고, 실제 100,000건에서 목록·신규·재사용·복구·정리·검사·마무리 시간을 각각 측정해야 합니다.

근거: [mb_window.basfrag](../development/mb_window.basfrag)의 `MBW_CanCommit`; [mb_window_declarations.basfrag](../development/mb_window_declarations.basfrag)의 `MBW_AUDIT_LIMIT`; [mb_archiveaudit_declarations.basfrag](../development/mb_archiveaudit_declarations.basfrag)의 `MBA_FILE_BUDGET`; [mb_identity_declarations.basfrag](../development/mb_identity_declarations.basfrag)의 `MBI_MAX_CANDIDATES`; [mb_metrics.basfrag](../development/mb_metrics.basfrag)의 `MBF_Forecast`.

### G01 — 실제 대상 환경의 필수 검증이 남음

**P1 검증 공백. 확인된 컴파일 오류라는 뜻은 아닙니다.**

실제 클래식 Outlook에서 BAS 가져오기·`Debug > Compile VBAProject`, 첫 실행 네이티브 자체 검사, 기존 MSG·재가져오기·내용 변경·복구 조합을 실행한 증거가 없습니다. 100,000건의 전체 시간과 Outlook 메모리 사용량도 미측정입니다. Windows CI에서 실행한 것은 Python 검사입니다.

현재 파일은 복사한 대표 아카이브와 테스트 프로필에서 이 단계부터 검증해야 하며, 대규모 실사용 검증이 끝났다고 승인하지 않습니다. 전체 임의 MAPI 속성이나 모든 특수 첨부를 인증 범위로 확장하지 않습니다.

근거: [실제 Outlook 검증 절차](OUTLOOK_VALIDATION.md), [검증 기록](validation.json), [mb_acceptance.basfrag](../development/mb_acceptance.basfrag).

## 사용자 시나리오와 종·횡 연결 검토

입력 상태를 신규·기존·재가져오기·내용 변경으로 나누고, 운영 상태를 정상·일부 손실·전체 메타데이터 손실·경로 변경으로 나눴습니다. 각 경우에 선별 → 검증 → 기록/게시 → 결과 표시 → 다음 실행/복구가 이어지는지 확인했습니다. 이 표는 핵심 상태 전이 검토이며 가능한 모든 환경 조합의 완전 증명이 아닙니다.

## 개선 및 확인 우선순위

1. **대상 PC 실행 근거 확보:** 정확한 BAS의 컴파일과 네이티브 자체 검사, 복사한 대표 아카이브에서 파일 수·바이트 해시·재실행 중복 여부를 확인합니다.
2. **R01 과거 증거 연속성 보완:** 스냅샷에만 남은 기록을 놓치지 않게 하고, 독립 proof의 존재/부재와 유효 행 유실·혼합 부분 복원 조합을 검사합니다.
3. **R02 이전 사용자 지정 MailBackup 루트 처리:** 명확한 구형 증거와 설정 삭제 후 재발견까지 포함해 판정하고, 문서와 계약을 일치시킵니다.
4. **R03/R04 REVIEW 해소·비용 측정:** 근거별 안내와 안전한 재처리 절차를 갖추고 성공 범위 반복 비용을 측정합니다. 보호 조건을 제거해 완료로 표시하지 않습니다.
5. **실제 규모·문화권 검증:** 일반/HTML/Unicode/긴 제목/첨부/재가져오기/시간대 변경을 확인하고, 실제 100,000건의 초기·증분·복구 시간을 분리 기록합니다.

구조만 다시 검토해서 100점을 부여하지 않습니다. 발견 사항을 보완하고 대상 실행 증거까지 확보한 다음 같은 기준으로 재평가해야 합니다.
