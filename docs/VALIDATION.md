# v3.4.0 검증 결과와 적용 범위

이 문서는 **코드 작성 환경에서 확인한 결과**와 **실제 Outlook에서 아직 확인하지 못한 결과**를 구분합니다. 문법 검사, Python 모델 검사 및 설계 검토 점수는 Outlook 실행 인증이나 모든 기존 MSG의 호환성 보증을 의미하지 않습니다.

이 검사는 표준 라이브러리 기반의 상태·실패 모델과 소스 계약을 다룹니다. Python 모델이 통과했다고 동일한 COM 호출, 파일시스템, 레지스트리 및 Outlook 공급자 동작까지 실행한 것은 아닙니다.

저장소 루트에서 `python tools/test.py`로 7개 모음을 재실행할 수 있습니다. `python tools/build.py --check`는 개발용 조각에서 배포 BAS를 정확히 재생성할 수 있는지 확인합니다.

문법 검사는 ANTLR VBA 문법으로 각 선언·프로시저 단위를 분석했고, 별도로 전체 모듈의 조립과 심볼 연결을 정적으로 확인했습니다. 공개 매크로는 하나이며, 최장 물리적 줄은 326자, 최장 연속 줄 연결 수는 18개였습니다. CRLF가 아닌 줄바꿈은 없었습니다.

**Microsoft Office의 VBA 컴파일러로 전체 프로젝트를 컴파일한 결과는 아닙니다.** 실제 Office 버전의 제한, 참조 설정, API 선언의 실행 결과는 대상 Windows PC에서 확인해야 합니다. 과거 단계의 전체 모듈 문법 검사 결과를 최종 파일의 Office 컴파일 결과로 사용하지 않습니다.

ANTLR 기반 작성 단계 검사는 위 결과의 근거이며, `tools/test.py`가 ANTLR 검사를 수행하는 것은 아닙니다. 작성 당시의 결과는 [검증 기록 JSON](validation.json)에 보존했습니다. ANTLR 런타임과 작성 단계 검사 도구는 이 저장소에 포함하지 않았습니다.

## 기존 회귀 검사

작성 단계에서는 무결성 31개, 복구 18개, 보관 파일 검사 16개, 저장소 연결 12개, 임시 단계 복구 10개, 파일명 17개 등의 기존 검사도 확인했습니다. 운영 상태 회귀 검사는 17개 통과와 1개 명시적 제외로 기록했습니다.

제외한 항목은 이전 이관 정책에서 활성 상태를 삭제·교체하길 기대하던 검사입니다. v3.4는 살아 있는 활성 증거를 보존하므로 이 기대를 유지하지 않았으며, 새 설정 검사에서 덮어쓰기 방지 계약을 확인했습니다. 복구의 전체 재조정 조건과 신규 검증 라벨 변경도 새 정책에 맞춰 명시적으로 갱신했습니다.

추가 assertion 모음의 기록은 acceptance 732, compatibility 85, 연·월 140, 이전 무결성 18,015, legacy 라벨 호환 96, locale 256, identity 61개입니다. 이 숫자는 위의 243개 새 테스트와 단위가 같지 않으므로 합쳐 하나의 “실행 검증 건수”로 표시하지 않습니다. 저장소 기본 실행 도구는 7개 v3.4 모음을 대상으로 합니다.

## 검증이 확인하려는 주요 불변 조건

1. **원본 증거의 우선순위:** 이미 기록된 기대 해시·크기는 새로 관측한 바이트와 구분합니다. 현재 파일이 열린다는 이유로 충돌한 과거 기대값을 바꾸지 않습니다.
2. **재실행 가능성:** 복구와 이동은 확인된 계획 및 START/DONE 또는 PREPARE/COMMIT 기록에 연결됩니다. 중단 후 임의의 다른 계획으로 바꿔 완료 처리하지 않습니다.
3. **계정 경계:** 관리 루트, 계정 폴더, 복구 표식, 원본 참조의 StoreID·소유권을 확인합니다. 다른 저장소의 증거를 묵시적으로 같은 메일에 연결하지 않습니다.
4. **보관 완료의 근거:** 임시 저장, 다시 열기, 지원하는 내용 비교, 해시·크기 확인, 최종 게시 및 인덱스 기록을 구분합니다. 확인하지 못한 단계를 성공으로 계산하지 않습니다.
5. **독립된 검사 범위:** 현재 메일 수집, 과거 원본의 내용 검사, 실제 보관 파일의 무결성 검사와 기준선 출처는 별도 상태를 갖습니다.
6. **호환성의 방향:** 이전 파일과 검증 라벨을 읽어 재검사·재사용합니다. 새 운영 상태를 이전 작성기가 이해한다고 가정하지 않습니다.
7. **성능 수치의 출처:** 신규 저장과 기존 재사용의 표본을 구분합니다. 관측하지 않은 실제 10만 건 처리 시간을 측정값처럼 표시하지 않습니다.

이 조건들은 구현과 모델의 계약입니다. 실제 Outlook에서의 실행 결과까지 모두 입증한 목록은 아닙니다.

## 자동 처리를 멈추고 검토하는 경계

| 경계 상황 | 보수적인 처리 |
| --- | --- |
| 동일 키에 서로 다른 과거 기대 해시 | 어느 쪽이 맞는지 임의 선택하지 않고 충돌 보존 |
| 알 수 없는 체크섬 포함 스키마, 끊어진 의미 참조 | 기록을 보존하고 명시적 검토 요구 |
| 충분한 게시 증거가 없는 부분 임시 파일 | 성공 메일로 인정하지 않고 보존·검토 |
| 분기된 이동 이력, 잘못된 바이트 경계의 기록 | 복구를 중지하고 이력 검토 |
| 구버전에서 중단된 복구의 보존 기록에 정확한 연결 증거가 없음 | 자동 병합을 확정하지 않음 |
| 다른 StoreID 또는 소유권 충돌 | 계정 연결 및 자동 작업을 확정하지 않음 |
| 보수적 기준보다 오래된 메일과 기존 MSG가 연결되지 않음 | 과거 파일 재내보내기를 피하기 위해 미연결·검토로 남길 수 있음 |
| `UserProperties` 또는 지원하지 않는 특수 첨부파일 | 전체 내용이 같다고 인증하지 않음 |

MSG만 남은 경우의 `MSG_ONLY_REBASELINED`는 **현재 읽은 바이트의 기준선**입니다. 없어진 이전 해시, 원본 식별자, 과거 내용의 완전한 동일성을 복원하는 상태가 아닙니다. 모든 메타데이터와 MSG 자체가 함께 사라지면 이 모듈의 복구 범위를 벗어납니다.

## 설계 평가 점수의 해석

v3.4 작성 단계의 설계·정적 검토는 반올림 **98/100**으로 평가했습니다. 이 숫자는 실제 Windows Outlook 실행을 포함한 운영 품질의 실측값이 아니며, 외부 인증이나 결함이 없다는 보증으로 사용하지 않습니다. 실제 컴파일·실행·기존 데이터 호환성과 대량 처리 관측을 마치지 않은 상태에서 “100점” 또는 “100% 상호 호환”으로 표시하지 않습니다.
