### R01: 보존한 과거 증거를 기준으로 복구

활성 파일이 snapshot보다 길다는 사실만으로 과거 행이 남아 있다고 판단하지 않습니다. snapshot의 정확한 과거 바이트 구간을 최대 64 KiB씩 순차적으로 해시합니다. 정상 append는 허용하고, 유효 행을 다른 유효 행으로 바꿔 길이를 유지한 경우도 탐지합니다.

복구가 필요하면 건강 검사에 사용한 **최신 읽을 수 있는 manifest**를 기준으로 고정합니다. 복구에 필요한 그 블록이 손상됐다는 이유로 더 오래된 snapshot이나 MSG-only로 내려가 누락된 과거 증거를 숨기지 않습니다. 이미 진행 중인 MERGE는 최초 불변 overlay 계획을 재사용합니다.

semantic merge는 허용된 빈 줄 등을 정상화할 수 있으므로, 병합 후 실제 결과 바이트를 새 snapshot에 기록한 뒤 DONE을 남깁니다. checkpoint가 실패하면 START와 최초 계획이 남습니다. 기대 해시를 현재 MSG 해시로 교체하지 않습니다. 관련 모델·소스 계약 39개와 실제 VBA에서 실행될 disposable fixture를 추가했습니다. fixture는 작성했지만 이 환경에서 실행하지 않았습니다.

근거: [복구 구현](../development/mb_recovery.basfrag), [39개 회귀 검사](../development/v351_recovery_continuity_models.py), [native fixture](../development/mb_operating_selftest.basfrag).

### R02: 이름 대신 확인한 구조를 기억

새로운 빈 `MailBackup`은 `State` / `_Recovery`를 사용합니다. V2/V3.3/V3.4 owner가 있는 기존 루트는 이름이 `MailBackup`이어도 `_MailBackup_Data` / `_MailBackup_Recovery`를 유지합니다. 이전 generic Schema4는 실제 구조 근거를 확인합니다.

기존 `owner.txt`를 `.Modern` 또는 `.Legacy`로 구체화하고 체크된 HKCU 복사본을 남깁니다. 별도 디스크 구조 설정 파일을 추가하지 않습니다. 이전 owner 원본은 보존합니다. 구조 힌트는 소유권·계정·StoreID 증명을 대신하지 않습니다. 남은 근거가 충돌하거나 일반 Schema4 `MailBackup`의 구조 단서가 모두 사라지면 중단합니다.

근거: [구조 선택 구현](../development/mb_layout_binding.basfrag), [57개 회귀 검사](../development/v351_layout_binding_models.py), [폴더 계약](PATHS.md).

### R03: 검토 사항을 구체적인 조치로 연결

`review.tsv`는 닫힌 이벤트 로그로부터 만든 파생 보고서입니다. 임시 보고서를 닫기·flush 후 게시하고, 실패는 최종 요약에 반영합니다. 경고가 나중에 해결되거나 같은 메일에 여러 행이 생길 수 있으므로 행 수를 고유 미해결 메일 수로 표시하지 않습니다.

`HISTORY_CUTOFF`에서 기존 아카이브·계정을 확인해 백업된 적 없는 개별 원본이라고 판단할 수 있다면, 사용자가 Unicode MSG를 한 번 제공하고 같은 매크로의 기존 파일 비교 경로로 검증받을 수 있습니다. 자동 재내보내기·일괄 강제 승인·해시 수정 기능은 추가하지 않았습니다. 누락·변조·충돌 증거의 우회 절차로 사용하지 않습니다.

근거: [보고서 구현](../development/mb_review.basfrag), [46개 회귀 검사](../development/v351_review_guidance_models.py), [사용자 해소 안내](REVIEW_GUIDE.md).

### R04: 성공 판정과 선별 성능을 분리

캐시는 유효한 성공 coverage가 이미 있고, 초기·복구·정책 변화·전체 재검사가 아니며, 전체 목록과 계획된 처리를 끝내고 남은 REVIEW 각각을 source-audit 원장에 기록한 경우에만 발행합니다. close·flush 뒤 발행하며, critical checkpoint 오류 처리가 끝난 뒤 optional cache를 처리하여 오류를 숨기지 않습니다.

다음 실행은 루트·계정·StoreID·정책·시간대·기존 성공 UTC와 coverage/journal/source-audit SHA-256이 모두 같을 때만 캐시 시각에서 7일 중첩 범위를 적용합니다. pending·unknown·changed·이전 정책·순환 내용 검사는 계속 선별됩니다. 캐시가 없거나 달라지면 기존 성공 범위로 돌아갑니다. 성공 coverage와 복구 필요 토큰은 그대로 유지합니다.

`.cache`는 복구 snapshot에 넣지 않는 재생성 가능한 최적화입니다. 같은 source가 중복 집계되면 보수적으로 캐시를 발행하지 않을 수 있습니다. 10만 개 합성 기록에서 선별 건수 감소를 확인했지만 실제 Outlook 처리 시간이 감소한 비율을 측정한 것은 아닙니다.

근거: [선별 캐시 구현](../development/mb_selection.basfrag), [36개 회귀 검사](../development/v351_selection_models.py), [기존 강제 선별·완료 조건](../development/mb_window.basfrag).

## 종·횡 검토와 재실행의 연결

종방향은 **입력 판별 → 증거 검증 → 파일 작업 → 내구 기록 → 완료/REVIEW → 재시도**를 확인했습니다. 횡방향은 메일 상태·운영 기록 상태·실행 중단 시점을 분리해 다음 교차 조건을 검토했습니다.

| 교차 시나리오 | 유지한 조건 | 재실행 결과 |
| --- | --- | --- |
| 기존 MSG × 정상 기록 | 과거 기대 해시·지원 내용 비교 | 확인된 파일 재사용, 불필요한 SaveAs 없음 |
| 신규 메일 × 게시 중단 | 원본 보존, stage·두 곳의 intent·hash | 검증된 단계만 재개, 불명확한 임시 바이트는 보존·REVIEW |
| 재가져오기 × EntryID 변경 | 같은 StoreID와 내용 증거 | 검증된 별칭 연결 또는 REVIEW |
| 과거 행 삭제 × 겉보기 정상 파일 길이 | snapshot raw-prefix | 과거·이후 proof를 모두 보존하여 복구 |
| 복구 × 재시작 | 최초 overlay 계획, checkpoint→DONE | 동일 계획 재개, 정상 완료 후 반복 복구 방지 |
| 설정 삭제 × 운영/복구 기록 생존 | 정확한 위치·소유권·구조 근거 | 남은 근거로 복원하거나 한 번 선택 |
| 모든 metadata 소실 × MSG 생존 | 현재 바이트와 과거 무결성 구분 | MSG-only 현재 기준선; 사라진 역사 인증 금지 |
| REVIEW 지속 × 정상 완료 이력 | 개별 retry와 성공 coverage 고정 | 조건을 만족한 경우 상세 비교 범위만 줄임 |
| 캐시 삭제/변경 × 재실행 | 캐시와 증거의 정확한 binding | 캐시 무시, 기존 성공 범위 또는 full 유지 |
| 장기 미실행 × 오래된 신규/변경 메일 | 전기간 unknown/changed 선별 | 30일/90일 상한으로 누락시키지 않음; 불명확하면 REVIEW |
| 시간대/정책 변화 × 기존 cache | context와 정책 검증 | 전체 재검사, cache가 범위를 줄이지 못함 |

지원 범위 안에서는 정상·실패·검토·재시도가 연결됩니다. **모든 입력을 자동 성공 상태로 끝내는 닫힌 시스템은 아닙니다.** 입증할 수 없는 충돌이나 지원 불가 내용의 REVIEW는 의도된 결과이며, 이를 별도 판단 없이 성공으로 바꾸지 않습니다.

- **C06 취소·중단·재실행·완료시각:** critical checkpoint 오류를 확정한 뒤 optional cache를 호출하고, 닫기·flush·미처리·REVIEW 개별 의무를 확인. 실제 강제 종료·저장장치 장애 미실증.
- **C07 경로·소유권·계정 경계:** 구조 선택 힌트를 소유권 증명과 분리하고 정확한 root/account/store 연결 및 충돌 거부를 유지. 실제 Win32 경합과 임의 위치 이동 미인증.
- **C08 폴더명·선택·경로 재사용:** 명시 owner와 체크된 HKCU 구조 복사본, 두 구조의 생존 조합·삭제·재시작·충돌을 검증. 새 디스크 구조 설정 파일이나 개인 고정 경로 없음. 실제 Shell/HKCU 미실행.
- **C09 자동 범위·장기 미실행:** 장기 미실행·unknown/changed 전기간 선별을 유지하며, 정상 이력이 있는 archive만 exact-proof-bound partial selection을 재사용. 초기·복구·불확실한 과거 메일의 자동 완료 제한은 유지.
- **C10 일시·문화권·시간대:** ASCII/Gregorian/UTC·형식 변화 감지·달력 복원. 실제 로캘/DST/provider 조합 미실행.
- **C11 연월·파일명·Everything 검색:** 기존 이름 보존·제목 길이 예산·Unicode surrogate 보호·충돌 회피. 긴 제목·이미 축약된 이름을 모두 표현하지 못함.
- **C12 10만 건 성능·예측:** 반복 REVIEW로 넓어진 최근 범위의 불필요한 상세 비교를 10만 합성 항목으로 검증. 전체 metadata 순회와 prefix 해시 비용은 유지하며 실제 시간·메모리·10만 건은 미실측.
- **C13 단일 실행·결과 보고:** 단일 public macro 유지, 원인·제목·경로·조치를 review.tsv로 제공하고 PARTIAL과 사건 행 수를 구분. 생성 오류의 최종 상태 반영까지 검증. 일부 해소는 사용자 판단 필요.
- **C14 검증 도구·배포 추적성:** 558개 모델/소스 계약과 47개 검증기 검사, BAS 재조립·증거 해시·세 조건 분기 검사 통과. CI는 정확한 커밋의 결과로 별도 확인. 추가 ANTLR 환경은 저장소 기본 재현 범위 밖.

실제 대상 실행의 미부여분은 가중치 기준 **9.60점**입니다. 나머지 **2.39점**은 내용·호환성 범위, 자동 해소 한계, 전수 순회·새 해시 비용, 검증 도구 재현 범위 등에 대한 평가 여유입니다. 실사용을 한 번 성공했다고 남은 점수를 자동으로 모두 부여하지 않습니다.

## 남은 실제 확인과 사용 방법

사용자는 최종 BAS를 기존 모듈 대신 가져와 `Debug > Compile VBAProject`를 확인한 뒤 **`MB_01_RunBackup` 하나**를 실행합니다. 첫 실행의 비공개 native 검사가 자동으로 진행됩니다. SafeV2를 먼저 실행하거나 별도 순서별 매크로를 실행할 필요가 없습니다. 기존 MSG는 선택한 기존 계정 폴더에서 검증·재사용하고 `yyyy\mm`로 정리합니다.

실제 컴파일, synthetic native 결과, 대표 기존 MSG의 해시·내용·재실행 비교, 운영 파일 삭제·복구, 시간대·문화권, 실제 10만 건의 시간·메모리를 [Outlook 검증 절차](OUTLOOK_VALIDATION.md)에 따라 BAS SHA와 연결해 확인해야 합니다. 현재 환경에서는 이 작업을 실행할 Windows Outlook이 없으므로 NOT_RUN을 유지합니다.

과거 작성기와의 교대 쓰기, 이미 삭제된 MSG 복원, 임의 드라이브 이동 후 무조건 이어 쓰기, 모든 MAPI 속성 인증, 경로 한계를 넘는 전체 제목 보존은 지원 범위를 넘어섭니다.
